# Compiler centralization

Unreleased migration following the Python-package work. No publication or managed
installation upgrade was performed.

## Ownership and compatibility

The active compiler now lives under `ternela/compiler/`:

| Owner | Responsibility |
|---|---|
| `jobs.py`, `__main__.py` | Compile one saved local task; product subprocess entry point |
| `run.py` | Discovery, bounded expansion/replanning, manifests and final admission |
| `evidence.py`, `retrieval.py`, `feedback.py` | Public evidence selection, targeted reads and admission feedback |
| `inference.py` | CLI protocol, bounded attempts, exact stage reuse and compressed provenance |
| `guides.py`, `prompts/` | Verified pagination guidance and one canonical copy of compiler prompts |
| `schema.py` | Discovery schema; executable plans import the shared `ternela.plan_schema` |

The workbench launches `python -m ternela.compiler JOB_ID`. Runtime/compiler imports
have no dependency on lab or interface packages. The source boundary checker follows
the active compiler's imports transitively, including newly introduced helpers.
New source snapshots identify canonical `ternela/` code/prompts rather than unrelated
interface/lab implementation files.

Seven moved module paths remain module-identity aliases, preserving imports and mock
seams. The old workbench compiler command still works. Historical evaluators, schema
versions, regression fixtures, manifests, original blobs and explicit code locks are
retained. The generic research runner's default historical fixture directory remains
compatible; the product saved-task path supplies its own directory. A changed code
inventory rejects a previous explicit code lock; it does not relabel history.

## Evidence

- **411 unit/API tests** pass, including **20 new compiler tests**, and **41/41 known
  regression scenarios** pass with no structural audit issues. Ten retained local
  receipt cases also pass. Lint, format, whitespace and JavaScript syntax checks pass.
- A frozen archive of the pre-migration working tree was run alongside the migrated
  compiler. For a synthetic public GitHub release task, discovery/compilation payloads,
  exact prompts and schemas, expansion feedback, final plans and admission outcomes
  were identical. The run exercised discovery, compile-0 and compile-1.
- New tests exercise actual subprocess stdin, temporary schema/output files and event
  capture using a local CLI stand-in. They cover the workbench's background launch and
  saved-job recovery, old command/import identity, catalog boundaries, changed fixtures,
  existing-run preservation, repair, bounded fallback, retries/timeouts, completed invalid
  output, tool-attempt rejection, stage reuse and exclusion of private expectations.
- Wheels are built from the source distribution and installed with no index or runtime
  dependencies outside the checkout. Qualification verifies canonical compiler imports
  without lab/workbench modules, executes the complete offline compiler pipeline,
  exercises the public SDK/UI APIs, and completes the real reference-agent handoff.
  Installed code remains unchanged and application state stays outside site-packages.

The offline CLI stand-in makes **zero model requests**. It establishes orchestration
and migration behavior for these cases, not live model quality, external CLI-version
compatibility, universal semantic coverage or production reliability. Existing
inference flags, retry limits, schema contracts and prompts were preserved.

Compressed source freeze, comparison, failure/success logs and qualification receipts
are retained privately in ignored `data/audits/compiler-migration/`. They are excluded
from release/package evidence seeds. Public documentation and code remain concise;
there is no second compiler implementation, new runtime dependency or background daemon.
