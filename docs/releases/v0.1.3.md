# Ternela v0.1.3

Install Ternela as a Python package, or keep using the macOS container installer.
This release centralizes the compiler, separates installed code from local data,
and reduces repeated work in watch reads and Python-client session startup.
Ternela remains an Apache-2.0 single-host alpha with zero runtime Python dependencies.

## Choose an installation

**Existing container installation:** run `sh ~/ternela/ternela.sh update` using your
managed install folder. Saved watches, evidence, consumer positions and automatic
update consent are preserved. No host Python is needed.

**Python package on macOS (Python 3.11+):** download the wheel and `SHA256SUMS`,
verify its checksum, then install in a virtual environment:

```sh
python3 -m venv ~/ternela-python
~/ternela-python/bin/python -m pip install ./ternela-0.1.3-py3-none-any.whl
~/ternela-python/bin/ternela --data ~/ternela-data
```

Open the printed loopback URL and choose **Run agent demo**. The wheel includes
compressed, verified public source evidence, the UI and the reference-agent demo.
Installation adds no daemon or automatic updater. Upgrading/removing the wheel
preserves the separate data folder. These assets are on GitHub, not PyPI.

| Asset | Purpose |
|---|---|
| `ternela-v0.1.3.tar.gz` | Application bundle for the container installer/updater |
| `ternela-0.1.3-py3-none-any.whl` | Ready-to-install Python package |
| `ternela-0.1.3.tar.gz` | Python source distribution; build tools required |
| `SHA256SUMS` | SHA-256 checksums for all three artifacts |

For a new container installation, extract the **application bundle**, then run
`sh scripts/ternela.sh install`. Its first image build requires network access.
GitHub's generated source archives do not contain the prepared evidence seeds.

## Changes

- `ternela.compiler` owns the active pipeline, prompts, retrieval, inference and
  feedback. It uses shared plan schemas and admission. Legacy compiler imports and
  commands remain compatible; historical evaluators and fixtures stay separate.
- One path boundary separates read-only assets and writable state. Use `--data` or
  set `TERNELA_DATA` before importing application modules.
- Watch reads use one database connection for expiry and loading. A local synthetic
  benchmark measured a median reduction from 1.165 ms to 0.665 ms, about 43%.
- The Python SDK requests a compact session token rather than building the UI
  catalog: 55 bytes instead of 37,233 bytes in a clean test installation. Older
  servers remain compatible. Base imports defer the HTTP client until requested.
- Wheels and application bundles share the same verified public-evidence allowlist.
  Original user data, private research and generated reports are excluded.

## Validation and limits

411 unit/API tests and 41/41 existing simulated regression scenarios pass, with
20 new compiler tests covering real subprocess orchestration, retries, timeouts,
invalid outputs, bounded repair/fallback, private-expectation exclusion and reuse.
The before/after compiler comparison preserved exact prompts, inputs, plans and
admission for its authored offline task. CI also builds and probes the wheel.

Installed-package qualification exercises the full offline compiler pipeline, Python
client, UI APIs and actual reference-agent stop/resume demo. It has been exercised on
macOS/Python 3.15 and Linux containers/Python 3.11 and 3.15. Compiler tests use a local
CLI stand-in and make no model calls; they do not establish live model quality.
Local benchmark timings are not a production latency guarantee.

Supported host remains macOS. Stored database, plan and receipt formats are unchanged.
Container updates retain the immutable launcher and base image. No PyPI publishing,
authenticated connector or native Windows support is introduced.
